# Технологическая архитектура

На схеме показаны три независимых Kubernetes-кластера и один кластер PostgreSQL в трёх зонах. Независимые кластеры выбрала для изоляции отказов control plane и обновлений. Цена решения — отдельные развёртывания и мониторинг каждого кластера. Сервисы масштабируются горизонтально; для БД сначала увеличиваются ресурсы. При объёме 50 GB шардирование усложнит решение без подтверждённой необходимости.

Все записи идут через локальный `pg-writer` Service с двумя HAProxy. Каждый HAProxy проверяет `/primary` Patroni на всех узлах БД и отправляет SQL только текущему primary. Реплики сами по себе запись не принимают. PostgreSQL и etcd распределены по трём зонам; кворум etcd — 2 из 3. Patroni использует синхронный режим, `synchronous_mode_strict=true`, `synchronous_node_count=1`, `synchronous_commit=on` и обязательный watchdog для fencing. Потерявшая кворум сторона не продолжает запись. Если синхронного кандидата нет, запись приостанавливается: сохранность подтверждённых данных важнее приёма новых записей без репликации.

GeoDNS возвращает адрес доступного ALB с учётом здоровья площадки и сетевой близости; DNS не проксирует HTTP. Проверки ALB — каждые 5 секунд, исключение после трёх ошибок, TTL ответа — 30 секунд. Уже установленные соединения DNS не переносит: клиент переподключается, повторяя запись только с ключом идемпотентности. WAF и ALB не должны быть единственной общей точкой отказа; на схеме входной блок объединяет три независимых входа.

Статические страницы и ресурсы Web доставляет CDN из точек присутствия в регионах РФ, origin — Object Storage. Версионированные ресурсы имеют длительный cache-control, новые версии прогреваются. Персональные ответы API не кэшируются публично. CDN уменьшает географическую разницу времени загрузки страниц, но не делает задержку сети буквально одинаковой: результат оценивается по p95 из нескольких регионов, отдельно для страницы и API.

## RTO и RPO

При отказе одной зоны цель — автоматическое переключение за несколько минут без потери подтверждённых синхронных записей. Нужно проверить остановку primary, потерю зоны и разделение сети: запись должна остаться только на стороне с кворумом.

Для восстановления после потери всего кластера: pgBackRest full ежедневно, differential каждый час, непрерывный WAL archive с `archive_timeout=60s`. Копии хранятся 30 дней в отдельном регионе с отдельными правами. Алерт на задержку архива — 5 минут; до достижения 15 минут дежурная должна устранить сбой либо остановить приём записей, иначе RPO уже нельзя считать выполненным. Одной настройки `archive_timeout` без контроля доставки недостаточно.

Бюджет RTO 45 минут: обнаружение — 5, восстановление данных и WAL на заранее подготовленной площадке — 30, переключение — 5, проверка — 5. Для 50 GB закладывается не менее 50 MiB/с эффективной скорости восстановления базы и запас времени на WAL. Это требования к стенду восстановления, не результаты замера. Проверка backup выполняется ежедневно, контрольное восстановление и замер RTO/RPO — ежемесячно и после изменений. Доступность 99,9% оценивается отдельно по успешности пользовательских запросов; один допустимый RTO не доказывает выполнение SLO.
