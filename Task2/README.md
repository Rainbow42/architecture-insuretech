# Динамическое масштабирование

Нужны Minikube, kubectl и Helm. Все команды ниже выполняются из `Task2`. Скрипты написаны для bash; их можно запускать из fish командой `bash ...`. Они явно используют учебный context `sprint8-check`, приложение размещается в namespace `sprint8`, мониторинг — в `monitoring`. Остальные кластеры не изменяются.

## Подготовка

В Deployment закреплён digest оригинального образа `ghcr.io/yandex-practicum/scaletestapp`. Исходники приложения не меняются. Этот образ собран для amd64. На обычном Linux amd64 достаточно:

```sh
minikube start -p sprint8-check --cpus=3 --memory=6144 --keep-context
```

На Mac с Apple Silicon нужны установленная Rosetta, Minikube с драйвером vfkit и новый профиль с включённой эмуляцией:

```sh
minikube start -p sprint8-check --driver=vfkit --rosetta --cpus=3 --memory=6144 --keep-context
```

У уже созданной VM флаг `--rosetta` может не изменить параметры драйвера. Не удаляйте свой старый профиль: создайте другой и передайте его имя вторым аргументом в `run-experiment.sh` и первым в `prepare.sh`. Проверка регистрации эмулятора: `minikube -p sprint8-check ssh -- cat /proc/sys/fs/binfmt_misc/rosetta`. Если эмуляции нет, нужен amd64-стенд, а не замена приложения самописным сервисом.

```sh
bash prepare.sh sprint8-check
```

Скрипт устанавливает metrics-server, приложение, Prometheus chart `90.0.0` и Adapter chart `5.3.0`, дожидается готовности. Locust `2.46.6` запускается внутри Kubernetes и обращается к ClusterIP Service. `Connection: close` позволяет новым запросам попадать и в добавленные pod, а не оставаться на старых TCP-соединениях. Пробы приложения используют TCP, чтобы не увеличивать `http_requests_total` запросами проверки здоровья.

Если pod остаётся в `ContainerCreating` из-за загрузки образа, сначала посмотрите `kubectl --context sprint8-check -n monitoring describe pod <имя>`. На моём стенде загрузка из VM зависала; помогла загрузка того же образа через хост: `minikube -p sprint8-check image load --remote <точное-имя-образа-из-pod>`. После этого подготовку можно повторить. Менять образ приложения не нужно.

## Два эксперимента

```sh
bash run-experiment.sh memory sprint8-check
bash run-experiment.sh rps sprint8-check
```

Не запускайте их одновременно. Каждый запуск удаляет только предыдущий нагрузочный Job и два HPA этого приложения, возвращает одну реплику, перезапускает её для чистого начального состояния и сохраняет сырой вывод в `evidence/<режим>-<UTC>.log`. Перед нагрузкой скрипт до двух минут ждёт первую метрику нового pod: готовность приложения ещё не означает, что metrics-server успел его измерить. Повторный запуск не перезаписывает предыдущий лог. Нагрузка — 1000 пользователей, 50 новых пользователей в секунду, 5 минут, ожидание между запросами 1–5 секунд. Наблюдение продолжается 6 минут; один прогон с подготовкой занимает около 7–8 минут.

Для памяти цель HPA — 80% от `requests.memory=16Mi`, то есть 12,8 MiB, не от лимита. Лимит остаётся 30 MiB. Запрос 16 MiB выбран после калибровки: исходный сервис на этом стенде занимал около 8 MiB без нагрузки и 15 MiB в начале нагрузки; при запросе 20 MiB HPA сначала показывал 79% при цели 80%. Порог 12,8 MiB находится между измеренными значениями покоя и нагрузки. Для RPS цель — средние 10 запросов/с на pod, окно rate — 1 минута. Максимум в обоих случаях — 10 реплик. HPA учитывает допуск и интервалы синхронизации, поэтому не обязан срабатывать в ту же секунду, когда значение стало больше цели.

В логе нужно увидеть `SuccessfulRescale`, увеличение числа готовых реплик, успешное завершение Locust и отсутствие OOMKilled. Сам факт завершения скрипта ещё не доказывает масштабирование — его подтверждают значения HPA и Deployment. Если памяти мало для срабатывания, нельзя подменять лог: сохраните результат, измените обоснованно `requests.memory` или профиль нагрузки и повторите эксперимент. Нельзя повышать требуемый лимит 30 MiB или заменять сервис.

## Prometheus

В отдельном терминале оставьте работающей команду:

```sh
kubectl --context sprint8-check -n monitoring port-forward service/prometheus-kube-prometheus-prometheus 9090:9090
```

Откройте `http://localhost:9090`, раздел Query → Graph. Запрос:

```promql
sum by (pod) (rate(http_requests_total{namespace="sprint8",service="scaletestapp"}[1m]))
```

Снимок должен включать запрос, временную шкалу и легенду с именами pod. Во вкладке Targets источник `scaletestapp` должен быть UP. Port-forward здесь используется только для интерфейса Prometheus, не для нагрузки на приложение.

После проверки стенд можно остановить без удаления данных: `minikube stop -p sprint8-check`.
