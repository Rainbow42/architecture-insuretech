# Анализ текущей архитектуры

## Какие проблемы есть сейчас

1. Ответ `ins-product-aggregator` зависит сразу от нескольких внешних API. Если хотя бы одна страховая отвечает медленно, задерживается весь запрос. После подключения ещё пяти компаний таких ситуаций станет больше.
2. Копии тарифов обновляются с разной частотой: в `core-app` раз в 15 минут, в `ins-comp-settlement` раз в сутки. Поэтому два сервиса могут работать с разными версиями одного тарифа.
3. При сбое ночного обновления данные в `ins-comp-settlement` останутся устаревшими. В исходном описании нет политики повторов, поэтому её нужно определить отдельно.
4. Суточная выгрузка оформленных страховок из `core-app` со временем станет тяжёлым пакетным запросом. При повторе после тайм-аута возможны дубли, а при частичной обработке — пропуски.
5. В исходном описании не определены контроль свежести копий и обработка частичных ответов страховых. Без них можно не заметить пропущенное обновление.

## Предлагаемое изменение

Для продуктов и тарифов я выбрала поток событий. `ins-product-aggregator` опрашивает страховые по расписанию, раз в 15 минут, и публикует полный снимок каждого продукта в `product.updated`. Опросы разных страховых независимы; сбой одной не задерживает остальные. `core-app` и `ins-comp-settlement` читают топик своими группами потребителей и независимо обновляют локальные копии. Клиентский запрос больше не запускает цепочку внешних вызовов.

Оформленные страховки также передаются событиями. После оформления `core-app` сохраняет страховку и запись в outbox в одной транзакции. Отдельный relay публикует `policy.issued`, а `ins-comp-settlement` строит свою проекцию для месячного реестра. Суточный REST-запрос после этого не нужен.

Transactional Outbox нужен именно на стороне `core-app`: без него возможна ситуация, когда страховка уже записана в БД, а событие из-за сбоя не отправлено.

Relay выбирает записи с `FOR UPDATE SKIP LOCKED`, публикует их с `acks=all` и только после подтверждения отмечает отправленными. При сбое между подтверждением Kafka и отметкой в БД событие придёт повторно. Проверка `event_id` и изменение проекции выполняются одной транзакцией, Kafka offset подтверждается после commit.

Для агрегатора продуктов отдельную БД и Outbox не добавляла: источником остаётся API страховой, агрегатор отправляет полные снимки, а после сбоя повторяет опрос. Это даёт сходимость к актуальному состоянию, но не гарантирует сохранение каждой промежуточной версии тарифа. Если потребуется история всех изменений, понадобится версионированный API партнёра или его собственный поток событий. Ключ продукта — пара `insurer_id + product_id`, чтобы номера разных компаний не пересекались; устаревшие версии не заменяют новые. Пропуски частичного ответа не считаются удалением: удаление публикуется только после подтверждённого полного снимка.

Месячный реестр по-прежнему отправляет `ins-comp-settlement` через API страховой. Внешние протоколы REST / SOAP / GraphQL из исходной схемы не меняются. Сервис сохраняет состав реестра и статус отправки; `registry_id` используется для дедупликации, если это поддерживает партнёр. После неопределённого результата отправки сначала выполняется сверка, а не слепой повтор. Ответственность сервисов не меняется.

Сохранены B2B REST API `core-app`, платёжный сервис с HTTP-вызовом из `core-app` и redirect из Web, а также REST-вызовы `client-info` из Web и `core-app`. Эти взаимодействия не переводятся на Event Streaming.

Стек существующих сервисов сохраняется: Kotlin/Spring Boot, Web — JavaScript/React, базы данных — PostgreSQL. Relay использует тот же прикладной стек.

## Что потребуется учесть

- Доставка в Kafka будет как минимум однократной, поэтому обработчики проверяют `event_id` и допускают повтор события.
- Для сохранения порядка ключом партиции будет `insurer_id + product_id` или `policy_id`.
- Форматы событий нужно версионировать. В Schema Registry включается обратная совместимость.
- Для сообщений, которые не удалось обработать после повторов, нужен DLQ. Отдельные алерты нужны на consumer lag.
- Kafka разворачивается в трёх зонах: replication factor 3, `min.insync.replicas=2`, у продюсеров `acks=all`. При недостаточном ISR запись ждёт восстановления; события `core-app` остаются в outbox.
- В события передаются только необходимые данные. Соединения шифруются, права продюсеров и потребителей ограничиваются ACL.
