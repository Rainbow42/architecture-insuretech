# ОСАГО

Схема расширяет Task3: старые сервисы, события продуктов и страховок, клиентские данные и отправка месячного реестра сохранены. Добавлены `osago-aggregator`, его БД и два потока событий в том же Kafka. Значки Timeout, Retry, Rate Limiter и Circuit Breaker взяты из библиотеки задания и относятся к REST-вызовам страховых.

## Заявка и предложения

1. Web отправляет `POST /api/v1/osago/applications` с `Idempotency-Key`. `core-app` проверяет владельца и данные, сохраняет заявку и outbox одной транзакцией. Ответ — `202`, `application_id`, `accepted_at`, `deadline` и URL потока предложений. Повтор с тем же ключом и телом возвращает ту же заявку, с другим телом — `409`.
2. Relay публикует `osago.application.created`. Поля: `event_id`, `schema_version`, `application_id`, `accepted_at`, `deadline`, данные для расчёта. Ключ партиции — `application_id`.
3. `osago-aggregator` сохраняет входное событие и задачи по страховым одной транзакцией, затем подтверждает offset. Уникальные ключи — `event_id` и `(application_id, insurer_id)`. Воркеры берут задачи через lease с версией; просроченную задачу может забрать другой pod, запись результата разрешена только текущему владельцу lease.
4. Воркеры вызывают POST страховой, сохраняют её `request_id` и опрашивают GET. Каждое предложение сохраняется вместе с outbox. Фоновый publisher отправляет `osago.offer.received`, не дожидаясь остальных компаний. Поля: идентификаторы события, заявки и страховой, предложение, версия и время получения. Для окончания расчёта есть `osago.finished` со статусами по всем страховым. На схеме эти результаты объединены в один блок.
5. `core-app` читает результаты общей consumer group. Предложение, обработанный `event_id` и запись клиентского журнала сохраняются одной транзакцией; offset подтверждается после commit. Авторизация, выбор предложения и оформление полиса остаются в `core-app`.

БД агрегатора хранит задания, lease, внешний `request_id`, состояние опроса, deadline, предложения, обработанные события и outbox. Поэтому рестарт pod не теряет ход расчёта. Outbox publisher допускает повтор публикации, потребители выполняют дедупликацию.

## Поток в браузер и несколько pod

Web открывает `GET /api/v1/osago/applications/{id}/offers` с `Accept: text/event-stream`. `core-app` проверяет доступ пользователя к заявке. События: `offer`, `insurer_timeout`, `completed`; SSE `id` — последовательный номер в журнале конкретной заявки. Счётчик увеличивается под блокировкой строки заявки в той же транзакции, чтобы номера не обгоняли commit.

Журнал хранится в общей PostgreSQL `core-app` 24 часа после закрытия заявки. Любой pod может обслужить соединение. Сначала pod устанавливает `LISTEN`, затем читает журнал после `Last-Event-ID` и переходит к выдаче новых записей. `NOTIFY` с идентификатором заявки выполняется в транзакции записи и после commit будит все слушающие pod. Сами предложения передаются из БД, а не из уведомления. Один LISTEN-канал на pod, не отдельное соединение БД на пользователя.

При потере соединения браузер переподключается с `Last-Event-ID`. После восстановления LISTEN, а также раз в секунду для активных заявок, pod дочитывает журнал: пропущенный сигнал не теряет предложение. Перечитывание можно объединять по активным заявкам одного pod. Повторные события браузер отбрасывает по `id`. Если курсор уже удалён, Web получает актуальный снимок через `GET /api/v1/osago/applications/{id}` и возобновляет поток с возвращённого курсора.

Буферизация SSE в Ingress выключена, heartbeat отправляется каждые 10 секунд, idle timeout балансировщика — 75 секунд. Лимит расчёта не сбрасывается при reconnect: `deadline = accepted_at + 60 секунд`. Это общий срок, включая очереди и повторы, а не 60 секунд на каждую попытку. По deadline `core-app` фиксирует итог из уже полученных предложений и закрывает поток; незавершённые компании получают `timeout`. Фоновый обработчик закрывает просроченные заявки даже без открытого SSE; переход состояния и итоговое событие выполняются одной транзакцией под блокировкой заявки, повторное закрытие ничего не меняет. При поступлении предложения проверяется тот же deadline. Агрегатор прекращает новые вызовы и отменяет активные, где это возможно. Поздние ответы сохраняются для разбора, но закрытую заявку не переоткрывают.

## Ограничения и сбои

- Rate Limiter: квота `Lᵢ` на каждую страховую общая для всех pod, атомарное получение разрешения через Redis. Квоты задаются по договору с партнёром, не выдумываются из числа реплик. При недоступности Redis новые вызовы приостанавливаются, а не идут без ограничения. TTL относится к ключам лимитера, не к доставке предложений.
- Circuit Breaker: отдельный для каждой страховой; общий статус и ограничение пробных запросов в Redis. После серии ошибок вызовы прекращаются на время охлаждения, в half-open допускается одна проба. Порог и период уточняются по статистике ошибок. Сбой одного API не блокирует другие.
- Timeout: соединение — до 1 секунды, весь запрос — до 3 секунд и не дольше оставшегося времени заявки. Если бюджета не хватает, новую попытку не начинаем.
- Retry: для GET — не более двух повторов с задержкой и jitter, только пока позволяет deadline и квота. Для POST повтор разрешён только при документированной идемпотентности страховой с тем же ключом. Если POST завершился неопределённо и API не позволяет сверку, состояние отмечается `unknown`, повторная заявка автоматически не создаётся.
- Для каждой страховой отдельная очередь и ограничение параллельных вызовов. Период polling начинается с 2 секунд с jitter и увеличивается при нехватке квоты. `429` учитывает `Retry-After`, но не продлевает общий deadline. Kafka недоступна — события остаются в outbox, без молчаливой потери.

## Пиковая нагрузка

2500 одновременно принятых заявок и 10 компаний — до 25 000 задач. Если все они ещё ожидают ответа и GET выполняется раз в 2 секунды, верхняя оценка — 12 500 GET/с суммарно, или 1250 GET/с на компанию, плюс POST и повторы. Это расчёт нагрузки, не результат теста и не обещание такой квоты партнёров.

Для одной компании за 60 секунд нужно успеть хотя бы создать 2500 заявок: в среднем около 42 POST/с, без учёта GET. Если договорные лимиты ниже, получить все предложения за минуту невозможно даже при увеличении числа pod. Поэтому доступность частичных результатов обязательна; до запуска продукта нужно согласовать квоты и проверить сценарий 2500 клиентов. Параллелизм воркеров ограничивается квотой и временем ответа партнёра, а HPA учитывает возраст очереди и количество активных SSE. Проверяются задержка от получения предложения до SSE, consumer lag, глубина очереди, тайм-ауты и нагрузка на журнал PostgreSQL.

Ссылки: [LISTEN](https://www.postgresql.org/docs/current/sql-listen.html), [NOTIFY](https://www.postgresql.org/docs/current/sql-notify.html). Уведомления ускоряют доставку; восстановление обеспечивает сохранённый журнал.
