# Ограничение запросов

Ключ ограничения — IP клиента (`$binary_remote_addr`). `rate=10r/m` задаёт скорость, `limit_req_status 429` — ответ на превышение. `burst` не используется: накопленная пачка запросов не пропускается. Nginx применяет leaky bucket, то есть равномерную скорость примерно один запрос за шесть секунд, а не правило «первые десять пропустить, потом ждать границу календарной минуты».

Исходный upstream с тремя серверами сохранён. В тесте эти имена разрешаются в контейнер с HTTP 200, чтобы ошибки недоступного upstream не выдавались за успешную проверку.

Запуск из Task6 при работающем учебном Minikube:

```sh
bash run-test.sh sprint8-check
```

Скрипт использует `nginx:1.29.1-alpine`, проверяет исходный конфиг через `nginx -t`, затем отправляет 68 запросов с интервалом около секунды. Проверяется первый HTTP 200, отклонение следующего запроса с 429, восстановление пропускной способности и не более десяти принятых запросов в каждом скользящем окне 60 секунд. Сырой вывод сохраняется в `evidence/`; два тестовых контейнера и их сеть удаляются после прогона. Если сеть с таким именем уже существует, скрипт останавливается, не трогая её.

Результат проверки 4 октября 2026 года: `nginx -t` прошёл, за 68 запросов получено 12 ответов 200 и 56 ответов 429; в любом скользящем окне 60 секунд принято не больше десяти запросов. [Полный лог](evidence/rate-limit-20261004T161946Z.log). Первый прогон с ошибкой удаления временного конфига сохранён в `evidence/attempts/`; права очистки исправлены, итоговый прогон завершился успешно.

За внешним reverse proxy потребуется отдельно настроить real_ip только для доверенных адресов прокси, иначе ограничение будет общим для его IP. В исходном задании такой прокси не задан. IP также не заменяет идентификатор партнёра, если несколько партнёров работают через общий NAT.

[Документация Nginx](https://nginx.org/en/docs/http/ngx_http_limit_req_module.html).
